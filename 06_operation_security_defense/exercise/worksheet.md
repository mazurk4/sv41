## 書き方のヒント

### どれを選んでも考えたいこと

- この脆弱性は **ログインなしで、自分の PHP コードが動く前に** 起きる。コードの書き方では防げない
- 判断を分ける材料: **攻撃が実際に始まっているか** / **止めたときの損失** / **更新が壊すリスク** / **お客さんへの説明**
- 1つの対応で完璧になることはない。**弱点を別の層で補う**(パッチ・ポート規制・WAF・監視・バックアップ)

### A. 止めるを選んだ人へ

- **全部止める? 一部だけ止める?**(例: メンテナンス画面だけ出す、カート・決済だけ止める)
- お客さんへの **告知はどこで出す?**(公式サイト・SNS)。混乱に乗じた **偽の「メンテナンスのお知らせ」メール** にどう注意を呼びかける?
- **いつ再開する?** 再開してよいと判断する条件は?
- 大セールはどうする?(延期・お詫びのクーポン など)
- 実例: 10月21日の夜、@nifty や全国生協連などが **予防のためにサービスを止めた**。infoQ・お名前.com も、被害が分かった時点でサービスを止めた

### B. すぐ更新するを選んだ人へ

- テストを最小限にするなら、**これだけは確かめる** ものは?(トップの表示・ログイン・カートに入れる・決済)
- 更新で **サイトが壊れたら、どう戻す?**(前のイメージのタグに戻す・バックアップ)
- 8.4.26 → 8.4.27 は **パッチ版**(修正だけ)。8.4 → 8.5 のような大きな変更とは違う
- 作業は `FROM` を確かめて、`docker compose build --pull` → `docker compose up -d`。`--pull` を忘れると古いまま
- 夜中に1人で作業するリスク(ミス・確認漏れ)をどう減らす?

### C. WAF で守るを選んだ人へ

- WAF は **リクエストの中身** を見て止める。この脆弱性を起こすリクエストを、**ルールで見分けられる?**
  - 参考: Cloudflare は、普通のルールだけでは足りないとして、**リクエストと応答を合わせて見る新しい検知の仕組み** を用意したと発表している
- **WAF を通らない裏口** はない?(サーバーに直接つながる入口が開いていたら、WAF は意味がない)
- WAF は **時間稼ぎ**。**いつまでに** 更新する?
- セール中に **誤検知** で、普通のお客さんを止めてしまわない?

### 組み合わせを選んだ人へ

- **順番** は? 例: 「今すぐ C でしのぐ → 朝までに B → それまでに攻撃の兆候が見えたら A」
- **切り替える条件** は何で判断する?(WAF のログ・監視・ニュースで攻撃が報告されたら、など)
